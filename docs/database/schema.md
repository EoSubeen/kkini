# 데이터 모델

실제 SQL의 기준은 `supabase/migrations/`의 순차 마이그레이션이다. 금액 입력과 계산 결과의 단위는 API 계약과 동일한 `KRW_10K`(만 원)이며 JSONB 안에서도 같은 단위를 유지한다.

## 주요 엔터티

| 엔터티 | 목적 | 소유권 |
| --- | --- | --- |
| `profiles` | 표시 이름과 서비스 설정 | `auth.users.id`와 1:1 |
| `households` | 가구 단위 기본 정보 | 생성 사용자 소유 |
| `household_members` | 본인·배우자·자녀·부모 정보 | 가구를 통해 소유 |
| `financial_input_snapshots` | 진단에 사용한 입력값과 버전 | 사용자 소유, 불변 스냅샷 |
| `calculation_snapshots` | 현재 진단·미래 타임라인·가족 안전망 계산 결과와 계산·가정 버전 | 입력 스냅샷에 연결, 불변 |
| `recipe_selections` | 선택 레시피와 주택 비교 설정 | 계산 스냅샷에 연결 |
| `check_plans` | 실행 계획 묶음과 상태 | 사용자 소유 |
| `check_items` | 실행 체크리스트 항목, 완료 상태와 기한 | 점검 계획에 연결 |

## 공통 필드 원칙

- 기본키는 UUID를 사용한다.
- 사용자 소유 행에는 `user_id`, `created_at`을 둔다. 수정 가능한 행에만 `updated_at`을 두고 트리거로 갱신한다.
- 진단·레시피 결과에는 `calculation_version`과 `assumption_version`을 둔다.
- 구조화가 필요한 입력·결과는 버전과 함께 JSONB에 저장한다. API의 Zod 계약을 통과한 값만 기록한다.
- 입력·계산 스냅샷에는 UPDATE 정책을 만들지 않아 과거 계산 근거를 덮어쓸 수 없게 한다.
- 입력·계산·레시피 스냅샷은 `persist_calculation_snapshot` 함수에서 한 트랜잭션으로 기록해 일부 행만 남는 상태를 막는다. 함수는 `SECURITY INVOKER`와 RLS를 그대로 적용한다.
- 민감한 원문 입력을 로그나 분석 이벤트에 복제하지 않는다.

## RLS 원칙

- 브라우저에서 접근 가능한 모든 사용자 데이터 테이블은 RLS를 활성화한다.
- 기본 정책은 거부이며 `auth.uid() = user_id` 또는 검증된 가구 멤버십만 허용한다.
- 서비스 역할 키는 클라이언트 번들에 포함하지 않는다.
- 정책 테스트는 소유자 허용, 타 사용자 거부, 비로그인 거부를 각각 포함한다.

## 관계 무결성

- 자식 테이블은 `(참조 id, user_id)` 복합 외래키를 사용한다. RLS를 우회하더라도 다른 사용자의 가구·입력·계산·점검 데이터와 연결할 수 없다.
- 회원가입 시 `auth.users` 트리거가 `profiles`를 만든다. 프로필 임의 INSERT 정책은 제공하지 않는다.
- `financial_input_snapshots.household_id`는 MVP에서 선택값이다. 가구 편집이 완료된 흐름에서는 같은 사용자의 가구 ID를 연결한다.

## 삭제·복구

- 사용자 삭제 시 해당 사용자의 데이터는 외래키로 함께 삭제된다.
- 입력 스냅샷 삭제 시 연결된 계산과 레시피가 함께 삭제된다.
- 계산 스냅샷을 삭제해도 점검 계획은 남고 `calculation_snapshot_id`만 비워진다.
- 마이그레이션 롤백은 관리형 Supabase의 백업 또는 새 프로젝트에서 이전 마이그레이션까지 재적용하는 방식으로 수행한다.
